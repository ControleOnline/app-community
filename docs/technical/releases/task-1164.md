# Single Item POS delivery — task 1164

Canonical task: https://github.com/ControleOnline/app-community/issues/1164

## Scope

The POS starts from the saved device configuration and the authorized company/session stores. Single Item opens the catalog with a fresh empty draft; explicit order reopening and checkout back navigation keep the existing selection. Selecting a different product replaces the previous choice; selecting it again clears it. Completed sales clear the in-memory selection. Waiter/table/tab entry remains on its existing path.

Checkout uses the existing cash, receipt and loyalty rules. A reopened partially paid sale charges only the remaining amount, excluding cancelled receipts and respecting shared invoice allocations. Receipt reads fail closed and the balance is checked again before payment. Device loyalty `none` skips identification; `stamp` retains identification, optional skipping, accrual at the existing completion step and redemption. The sale's provider scopes loyalty and financial operations.

Company selection uses the authorized people store and persisted session choice. An unavailable selection is rejected, stale device responses are ignored, switching during a sale requires confirmation, and switching while payment is executing is disabled. The sale remains owned by its original company.

The compact POS shell uses company theme tokens, the shared company selector, account menu and bottom-bar preferences. The operational history excludes paid entries only when its explicit filter is requested. Automatic loading appends records without dropping the current page; totals and positive status counts come from the full authorized, filtered collection rather than the loaded subset.

## Publication ownership

Generic logic and regression tests belong to the source NPM packages and the Composer orders package. App-specific bootstrap/presentation adapters remain in the consumer. Overlay manifests pin exact numeric dependency versions and verify source/payload checksums before writing; code already incorporated into a package is verification-only. `ui-layout` retains its existing stable version: its app bootstrap adapter does not justify a separate generic package release.

The publication checkout is separate from the team's running local checkouts. No local database fixtures, environment files, credentials or customer recordings are delivered. There is no schema migration or production promotion in this task.

## Verification boundaries

Local browser validation covered small viewports, cash, partial payment and reopening, stamp/no stamp, skipping identification, redemption, product replacement/deselection, fresh entry after completion, company/session protection, profile/theme, bottom bar, history search/loading and totals. Package tests cover the corresponding state and authorization boundaries. Physical payment hardware and real gateway transactions were not validated. The intermittent profile-return network failure was not reproduced and is not claimed fixed.

Composer full-suite failures were compared with the installed stable baseline using the same dependencies: the existing failures remain identical, while the new focused contracts and waiter regression tests pass. Final package versions, source SHAs, build results and staging evidence are recorded on the task and frozen RC manifest.
